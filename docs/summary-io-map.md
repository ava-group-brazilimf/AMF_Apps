# Blueprint compatibility artifacts

`outputs/summary/compatibility/blueprint-compatibility-report.json` and
`blueprint-compatibility-report.md` are generated before Summary HTML
publication. The report contains camelCase diagnostics and `hashes` for raw
artifact, sanitized content, `D.staticDiagrams`, `renderAllDiagrams()` input,
`renderStaticDiagrams()` input, and `mermaid.render()` input.

Publication is permitted only when `publicationAllowed` is true for every
required Blueprint. A false decision leaves diagnostic reports available but
must not write or promote client-facing HTML.

# Summary Agent — Mapa de Artefatos de Entrada por Menu/Submenu

> **Baseado em**: `src/modules/ava-fabric-agents/summary/agents/summary-agent.md` (v1.4.0) e verificação
> direta do código real em `src/modules/ava-fabric-agents/summary/templates/html/summary-template.html`
> e `src/modules/ava-fabric-agents/summary/utils/build_summary_comprehensive.py`.
> **Propósito**: mapa canônico de todo artefato de `outputs/` consumido pelo Summary HTML, organizado
> por Fase → Menu → Submenu, com verificação linha-a-linha contra o código real do builder (não apenas
> transcrição da documentação do agente, que contém pontos de desatualização identificados abaixo).
> Todos os paths são relativos a `projects/{project_name}/outputs/`, salvo indicação contrária.
> Config do projeto sempre em `projects/{project_name}/context/project-config.yaml`.
> **Gerado em**: 2026-07-12, via 3 varreduras independentes de pesquisa cobrindo (1) Resumo Executivo + F1,
> (2) F2 + F3 + F4, (3) F5 + F6 + F7. **Coluna Remediation adicionada em 2026-07-12** — indica a solução
> definitiva para cada problema, sempre em duas partes:
>
> - **Classe A (fix permanente)** — mudança em `build_summary_comprehensive.py` e/ou
>   `summary-template.html` para que **todo summary novo já nasça correto**, independentemente do
>   projeto (nenhuma alteração hardcoded de stack/projeto — mesma premissa de todas as correções
>   anteriores deste módulo).
> - **Classe B (agente de remediação)** — o que `@ava-summary-remediation`/`remediate_summary.py` deve
>   fazer para summaries **já gerados**. Na maioria dos casos isso é `N/A — rebuild via builder corrigido
propaga automaticamente` (a Fase 6 do agente de remediação já reconstrói o HTML do zero usando o
>   template/builder corrigidos, então basta reexecutar o agente depois do fix de Classe A). Casos onde o
>   agente de remediação PODE ter um papel ativo adicional (ex.: reconciliar path de artefato divergente
>   sem sobrescrever dados existentes) estão marcados com ✅.

### 1.6 — Outros bugs de código encontrados

- **Bug de troca de chaves em `renderNavDots()`** (indicadores "done" na sidebar): o `dotMap` usa chaves
  `f6-pkg`/`f6-docs`/`f6-demo`/`f6-sec` para itens que na verdade são seções `f7-*`, e chaves
  `f7-iac`/`f7-ci`/`f7-cd`/`f7-parity` para o que são seções `f6-*`. Como `ndot()` busca
  `document.getElementById('nd-'+id)`, essas chaves nunca encontram o elemento real (`nd-f7-pkg` existe,
  `nd-f6-pkg` não) — as bolinhas verdes de progresso de **todos** os submenus de F6 e F7 nunca acendem,
  mesmo com os agentes concluídos.
  **Remediation**: Classe A — trocar as chaves do `dotMap` em `renderNavDots()` (F6 ↔ F7 invertidos).
  Classe B — N/A, rebuild propaga.
- **"Todos os Artefatos" (Resumo Executivo)**: dado é calculado normalmente (`build_artifact_inventory()`),
  mas não existe mais nenhum item de navegação ativo no sidebar para `s-artifacts` (removido
  intencionalmente — `validate_summary.py::_c4_4` exige sua ausência). O único botão que a referenciaria
  usa um seletor CSS que não casa com nada. Tela órfã, inacessível por navegação normal.
  **Remediation**: Classe A — decisão de produto pendente (reabilitar nav + relaxar `_c4_4`, ou remover a
  seção morta por completo). Classe B — N/A, depende da decisão.
- **4 seções de diagramas draw.io do F1** (`s-f1-diagrams-c4/-overall/-bpmn/-sequence`, injetadas por
  `patch_template_drawio.py`): HTML e `renderDrawioViewer()` funcionais, mas **sem nenhum item de menu**
  no sidebar atual (`validate_summary.py::_c4_2` exige explicitamente que não existam). Dado
  (`asis/drawio/*.drawio`) existe e é injetado, mas a tela nunca é alcançável pelo usuário.
  **Remediation**: Classe A — mesma decisão de produto pendente do item anterior. Classe B — N/A.
- **Fallback silencioso para AS-IS em C4 Context TO-BE**: quando `tobe/diagrams/c4-context.mmd` não
  existe, o builder reaproveita `asis/diagrams/c4-context.mmd` rotulado como se fosse TO-BE — pode
  induzir a erro de leitura por quem está avaliando a arquitetura alvo.
  **Remediation**: Classe A — adicionar badge/aviso visual explícito no card quando o fallback for usado.
  Classe B — N/A, rebuild propaga.
- **Bounded Contexts TO-BE sem fallback real**: quando `tobe/docs/bounded-context-map.md` está ausente,
  reusa os BCs AS-IS com padrão fixo "Clean Arch + CQRS" e ADR sintético (`ADR-00N`) — não vem de nenhum
  ADR real gerado pelo `adr-tobe.md`.
  **Remediation**: Classe A — marcar visualmente as linhas de fallback como "herdado do AS-IS, pendente de
  refinamento TO-BE" em vez de apresentar dados sintéticos como reais. Classe B — N/A, rebuild propaga.
- **Vários subtítulos citam arquivos nunca lidos** (texto estático desatualizado dentro do próprio HTML,
  não gerado dinamicamente a partir do parsing real): `value-chain.md` (F1 Documentação), `prototype-asis/`
  (F1 Fluxo de Telas), `gap-list-report.md` e
  `gap-analysis-summary.md` (F1 Gap List), `vulnerabilities.md` (Riscos), `tobe/api-map.md` (F2 API
  Surface), `tobe/nuget-packages.md` citado mas não parseado (F2 Tech Framework).
  **Remediation**: Classe A — corrigir cada `<p><span class="mono">...</span></p>` estático para citar
  apenas as fontes realmente lidas (ou implementar o parser real quando a fonte já existe, ex.
  `nuget-packages.md`). Classe B — N/A, texto estático, rebuild propaga.

### 1.7 — Divergências vs. `summary-agent.md` (documentação desatualizada, corrigir separadamente)

## 4. Recomendação de Follow-up

Os achados das Seções 1.1–1.6 (e detalhados linha a linha na coluna **Remediation** da Seção 2)
representam débito técnico real e não fazem parte do escopo desta tarefa de mapeamento
(auditoria/documentação) nem foram corrigidos neste momento. Caso o time decida corrigi-los, cada item já
está suficientemente detalhado (arquivo, causa raiz, e agora também a solução definitiva de Classe A/B)
para virar uma tarefa de remediação independente, seguindo o mesmo padrão de correção
project-independent já usado em `specs/015-summary-remediation-agent/`. Uma priorização sugerida, da
maior para a menor severidade percebida pelo cliente final:

1. **Dados 100% estáticos disfarçados de reais** (Seção 1.2) — risco de credibilidade mais alto, pois o
   cliente pode tomar decisões com base em números que não refletem o projeto real (ex.: Quality Gates,
   Critérios de Aceite, KPIs de Sizing sempre zerados/false).
2. **Divergências de path** (Seção 1.5) — fix rápido e de baixo risco (renomear string de path),
   desbloqueia chips que já deveriam funcionar.
3. **Tabelas mortas e dados órfãos** (Seções 1.1 e 1.4) — requer implementação de `render*()` nova, esforço
   médio.
4. **Funcionalidades não implementadas** (Seção 1.3 — Eventos AS-IS/TO-BE) — maior esforço (parser
   AST/regex novo); já mitigado no curto prazo pela mensagem "em desenvolvimento".
