## 2. Problem Statement

`docs/tobe-input-artifacts-existence-check.md` audited all 163 input-file references declared by
`orchestrator-tobe.md` (v2.4.0) against the real project `Meu-ERP-008-AST-LLM-Master-Orchestrator`,
finding 85 "NÃO" (file not found). The literal request was to correct every reference so that its
path exists under `{project_name}/outputs/*`.

Follow-up investigation (3 parallel exploration passes) established that this literal framing was
partly a false lead: project 008 was generated by a **path convention that predates a consolidation
already applied to the current agent spec files**. Cross-checking every referenced path against
each producing agent's own `## Output Contract` (the only reliable ground truth — not any single
project's on-disk layout) showed that the vast majority of the 85 "NÃO" rows fall into one of two
categories that require **no fix**:
1. The reference is already correct — it matches the current producer's Output Contract exactly;
   project 008's file happens to sit under an older, superseded name/path (e.g. the orchestrator
   correctly declares `outputs/tobe/docs/architecture-blueprint.md`, `outputs/tobe/db/sql-strategy.md`,
   `outputs/tobe/docs/tech-framework-document.md`, `outputs/tobe/risk-mitigation-plan.md`,
   `outputs/tobe/designer-system.md`, `outputs/tobe/user-journeys/user-journeys-report.md` — all
   confirmed to match their producer's current Output Contract verbatim).
2. The artifact was never produced for project 008 specifically (an AS-IS security/risk diagnostic
   that ran with reduced scope, a conditional Fase 4.2 PILOT step never triggered, etc.) — not a
   path bug.

Cross-referencing every path against its actual producer surfaced a much smaller, precise set of
**7 genuine defects** — references that resolve to no current producer under any name, or use the
wrong file extension / directory segment. These 7 are the scope of this PBI.

## 3. Decision

### 3.1 Ground truth = producer's `## Output Contract`, not any project's file layout

Confirmed with the user via `AskUserQuestion` before implementation: aligning to project 008's
physical layout would reintroduce path/name conventions already superseded by the current agent
specs, and would create new inconsistencies between producer and consumer. All 7 fixes below were
verified by reading the actual producing agent's Output Contract directly — not inferred from any
project's `outputs/` tree.

### 3.2 Seven confirmed defects, fixed

**AS-IS artifacts referenced by TO-BE agents (consumer-side fix only — no `asis-diagnostic` agent
touched, per explicit user scope confirmation):**

1. `outputs/asis/db/triggers-map.md` — no producer exists anywhere (`db-analyzer.md`'s Output
   Contract declares 7 outputs, none named this; trigger data only exists as an integer count
   field inside `db-type.json`). Fixed by **annotating** the reference in `database-policy-tobe.md`
   (Input Contract row 7) and `orchestrator-tobe.md` (mirrored Fase 1.4 table) as a **permanent,
   structural gap** — not redirected to a non-equivalent file, not silently removed.
2. `outputs/asis/docs/screen-flow.md` → `outputs/asis/docs/screen-flow.mmd` (wrong extension;
   `documentation-asis.md`'s FT skill only ever produces the Mermaid variant). Fixed in
   `designer-system-tobe.md`.
3. `outputs/asis/docs/test-plan.md` → `outputs/asis/qa/test-plan.md` (wrong directory segment;
   `bridge-fastqa-asis.md` writes to `qa/`, confirmed also in `orchestrator-asis.md`). Fixed in
   `orchestrator-tobe.md` (Fase 7.8 gate checklist + Input Contract table, 2 occurrences).

**TO-BE-internal (close out the remaining unresolved halves of `docs/tobe-architecture-io-map.md`
§4.6, §4.8, §4.9, §4.11):**

4. `outputs/tobe/docs/architecture-technical.md` → `outputs/tobe/docs/tech-framework-document.md`
   (no agent produces the old name; `architecture-technical-tobe.md` writes
   `tech-framework-document.md`). Fixed in `test-plan-tobe.md`, 15 occurrences (already
   non-blocking since `specs/016`; the dead path string itself was never corrected until now).
5. `outputs/tobe/architecture-design.md` → `outputs/tobe/docs/architecture-blueprint.md` (no
   producer for the old name; closest/actual equivalent is the blueprint written by
   `architecture-design-tobe.md`'s `CB` trigger). Fixed in `user-journeys-tobe.md`.
6. `outputs/tobe/architecture-design-tobe.md` → `outputs/tobe/docs/architecture-blueprint.md`
   (same dead reference, second half of io-map §4.8 — the first half, `sizing-report.md`, was
   already fixed in `specs/016`). Fixed in `azure-infra-estimator-tobe.md`, 6 occurrences (Read
   Priority list, `estimation_profile` decision table, READ ATTEMPT LOG format, 2 BDD scenarios).
7. `outputs/tobe/docs/test-plan-tobe.md` → `outputs/tobe/test-plan.md` (wrong `docs/` segment;
   `test-plan-tobe.md`'s own Output Contract has no `docs/` segment for this file — confirmed
   irregular but correct). Fixed in `developer-guide-tobe.md`, Input Contract row + 2 prose
   references in the Seção 7 template.

### 3.3 Residual verification — no fix needed

`outputs/tobe/migration-plan.md` (old path without `docs/`, fixed in `specs/016` for
`orchestrator-tobe.md` and `risk-mitigation-tobe.md`) — re-grepped across all of
`tobe-architecture/agents/*.md`: **zero residual occurrences**. The `specs/016` fix is complete;
no further action required.

## 4. User Scenarios (Given-When-Then)

### Scenario 1 — Resolvable reference now resolves (P1)

**Given** `architecture-design-tobe.md` (trigger `CB`) has already run and produced
`outputs/tobe/docs/architecture-blueprint.md`, **When** `azure-infra-estimator-tobe.md` executes
Step 1 Read Priority entry (2), **Then** the read now returns `READ_OK` instead of permanently
falling through to `NOT_FOUND` and the AS-IS enrichment fallback.

### Scenario 2 — Permanent, honestly-documented gap (P1)

**Given** no agent in the AS-IS pipeline produces a triggers-specific artifact under any name,
**When** `database-policy-tobe.md` or `orchestrator-tobe.md` documents this input, **Then** the
row is explicitly labeled as a permanent, non-blocking, structural gap — never silently removed,
never redirected to a file that isn't actually equivalent.

### Scenario 3 — Regression guard on renamed reference (P2)

**Given** `test-plan-tobe.md`'s Step 1d skip-logic degrades gracefully when its technical-stack
input is absent, **When** the reference is renamed from the dead `architecture-technical.md` to
the real `tech-framework-document.md`, **Then** the skip/fallback logic continues to function
identically — now against a file that is actually produced by Fase 2 in every normal run, instead
of a name nothing ever writes.

### Scenario 4 — Unrelated, already-correct references remain untouched (P2)

**Given** the majority of the 85 "NÃO" rows in `docs/tobe-input-artifacts-existence-check.md`
already match their producer's current Output Contract exactly, **When** this PBI's changes are
reviewed, **Then** none of those already-correct references (e.g. `architecture-blueprint.md`,
`sql-strategy.md`, `risk-mitigation-plan.md`, `designer-system.md`, `user-journeys-report.md`)
are modified — only the 7 confirmed defects are touched.

## 8. Assumptions

- `tech-framework-document.md` is an adequate redirect target for the 15
  `architecture-technical.md` references in `test-plan-tobe.md` — both cover the TO-BE technical
  stack (messaging, external APIs, microservices, resilience patterns) used to calibrate Step 1d;
  not independently verified that every field `test-plan-tobe.md` expects is present in
  `tech-framework-document.md`'s actual rendered output, consistent with the level of verification
  already applied to similar redirects in `specs/016`.
- `outputs/tobe/docs/architecture-blueprint.md` is the correct redirect target for both
  `architecture-design.md` and `architecture-design-tobe.md` dead references — both consumers
  (`user-journeys-tobe.md`, `azure-infra-estimator-tobe.md`) want a TO-BE architectural overview,
  which is exactly what the blueprint is.
- No live pipeline run was performed to observe the fix end-to-end — verification is
  structural/grep-based only, consistent with `specs/010`/`specs/013`/`specs/016`'s own
  verification approach for prose instruction files.
