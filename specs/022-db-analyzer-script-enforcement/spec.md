## 2. Current Problem Statement

Three distinct root causes were identified causing `ava-asis-db-analyzer` to produce generic, LLM-inferred artifacts instead of data-grounded outputs:

### 2.1 — Script Non-Execution (CRITICAL)
The agent has a rule in `ava-asis-solution-delphi` (Step 18.3) that `er-diagram.mmd` MUST be generated by `python src/shared/tools/gen_er_diagram.py`, piped through `validate_diagram.py`. However, `ava-asis-db-analyzer` produces its own `er-diagram.mmd` directly via `Write` — bypassing both scripts. This results in diagrams with ~10 generic tables instead of the real 103+ tables.

### 2.2 — Data Format Mismatch (CRITICAL)
`04_database_schemas.json` (from the Delphi AST analyzer) contains **DFM component field definitions** (e.g., `TFDQuery.Fields`, `TDBGrid.Columns`) keyed by **Delphi unit name** (`UPontoMarcacao`), not SQL DDL. The agent expects `payload.tables[]` to contain DDL-like `{name, columns[]}` but the actual format is:
```json
{
  "UPontoMarcacao": {
    "_compaction": "table",
    "_schema": [{"name":"delphi_type","type":"string"},{"name":"name","type":"string"}],
    "_rows": [["Integer","ID"],["Integer","ID_COLABORADOR"],["Date","DATA_MARCACAO"]]
  }
}
```
Without a transformation step (unit name → SQL table name, DFM fields → DDL columns), the agent cannot consume this data and falls back to LLM inference.

### 2.3 — Missing Post-Generation Completeness Assertion (HIGH)
No agent in the pipeline validates that generated artifacts contain a meaningful percentage of the source data. Example missing assertion (now implemented via in-memory counters):
```
ASSERT diagram_entity_count >= 0.8 * schema_table_count
```
Without this, silent data loss goes undetected — the agent reports success with 10 generic tables while 103 real tables exist in the source.

## 5. User Scenarios (Given-When-Then)

### Scenario 1 — Nominal Path: AST Data Consumed & Script Executed (Priority: P1)

**Story**: As the migration orchestrator, I want `ava-asis-db-analyzer` to consume real AST artifacts and execute required Python scripts so that the generated ER diagram and schema inventory reflect the actual legacy system data.

**Why this priority**: Without this, all downstream TO-BE database design, API contracts, and migration planning are based on fictional generic tables — invalidating the entire migration.

**Acceptance Scenarios**:

1. **Given** `legacy_technology == "delphi"` and `04_database_schemas.json` exists in `outputs/asis/delphi-ast-raw/compressed/`, **When** the agent executes, **Then** it applies the DFM-to-DDL transformation with the following deterministic rules:
   - **Unit-name-to-table-name**: Strip leading `U` prefix (if present); convert remainder from `CamelCase` → `UPPER_SNAKE_CASE` (e.g., `UPontoMarcacao` → `PONTO_MARCACAO`). If no `U` prefix, apply `CamelCase` → `UPPER_SNAKE_CASE` directly (e.g., `DataModule1` → `DATA_MODULE1`). If ambiguity remains, preserve original unit name in `Purpose` column.
   - **DFM-field-to-DDL-column mapping**: Map each row of `_rows` to `{name, type}` using this explicit type table:
     | Delphi DFM Type | DDL Simple Type |
     |-----------------|-----------------|
     | `Integer`, `SmallInt`, `LargeInt`, `TLargeInt` | `int` |
     | `String`, `WideString`, `Memo`, `Variant` | `string` |
     | `Date`, `Time`, `DateTime`, `TDateTime` | `datetime` |
     | `Float`, `Currency`, `Real`, `Extended` | `decimal` |
     | `Boolean` | `boolean` |
     | `TBytes`, `TGraphic`, `Blob` | `blob` |
     | *(unmapped)* | `string` (fallback) |
   - The agent produces `schema-inventory.md` with all discovered tables using the canonical 5-column template.
2. **Given** the above, **When** generating `er-diagram.mmd`, **Then** the agent invokes `python src/shared/tools/gen_er_diagram.py` (or equivalent deterministic script) and pipes output through `validate_diagram.py`, rather than writing raw Mermaid directly.
3. **Given** execution completes successfully, **Then** the post-generation assertion `diagram_entity_count >= 0.8 * schema_table_count` passes, where both counts are tracked in-memory during generation (not by reading files), `AgentResult.success` is true, and `AgentResult.artifacts` lists all files.

---

### Scenario 2 — Edge Case: AST Format Unrecognized (Priority: P2)

**Why this priority**: Defensive handling when AST schema evolves or is malformed.

**Acceptance Scenarios**:

1. **Given** `04_database_schemas.json` exists but its internal structure does not match expected `_compaction="table"` with `_schema`/`_rows`, **When** the agent executes, **Then** it logs a structured warning in JSON format:
   ```json
   {"warning_type": "ast_format_unrecognized", "file": "04_database_schemas.json", "expected": "_compaction:table", "actual": "<first_observed_key_type>", "fallback": "sql_inline_detection"}
   ```
   falls back to the existing SQL-inline/connection-string detection path, and still produces `schema-inventory.md`.
2. **Given** the above fallback, **Then** `AgentResult.success` is true, `AgentResult.risk.level` is 'medium' (due to incomplete source data), and the completeness assertion is skipped or adapted to available data.

---

### Scenario 3 — Quality Gate: Completeness Assertion Failure (Priority: P1)

**Why this priority**: Safety gate — must never silently produce incomplete artifacts.

**Acceptance Scenarios**:

1. **Given** the agent tracks `schema_table_count = 103` (incremented in-memory as each table is written to `schema-inventory.md`) and `diagram_entity_count = 10` (incremented as each entity is emitted to the diagram generator), **When** the post-generation assertion `diagram_entity_count >= 0.8 * schema_table_count` runs, **Then** it fails (10 < 82.4), `AgentResult.success` is false, `AgentResult.risk.level` is 'critical', and `AgentResult.human_gate_required` is true.
2. **Given** the above failure, **Then** a diagnostic message is emitted identifying the gap ("ER diagram contains only 10 of 103 expected tables; script execution or AST ingestion may have failed").

## 9. Assumptions

- `projects/{project_name}/outputs/asis/delphi-ast-raw/compressed/04_database_schemas.json` follows the documented `_compaction: "table"` format with `_schema` and `_rows` arrays
- `src/shared/tools/gen_er_diagram.py` exists and accepts `--project`, `--input`, and `--output` arguments; it produces `flowchart TD` syntax (not `erDiagram`) and exits with code `0` (PASS), `1` (FAIL — validation error), or `2` (FIXED — auto-corrected and written)
- `src/shared/utils/validate_diagram.py` exists and accepts piped Mermaid content with `--output`
- The agent's `Bash` tool is available (already in `allowed-tools`)
- **Entity counting method**: In `flowchart TD` output from `gen_er_diagram.py`, each diagram entity corresponds to a node declaration matching the regex `^[A-Z0-9_]+\["`. The in-memory counter `diagram_entity_count` is incremented once per emitted node. The in-memory counter `schema_table_count` is incremented once per table written to `schema-inventory.md`.
