## Decision 1 — AST JSON Schema Parsing Strategy

**Question**: How should the agent parse the three AST JSON files to extract business rule data for PBI composition?

**Decision**: Parse the `payload` structure defined by schema version `"0.1.0"`:
- `01_business_rules.json`: iterate `payload.rules.rows[]` — each row follows the schema array `["type", "unit", "method", "target", "expression", "source_ref", "id"]` → extract `id` (BR-NNN) + `target` + `expression` for acceptance criteria
- `02_form_business_rules.json`: iterate `payload.forms.rows[]` — each row follows schema `["form_name", "form_class", "source_file", "field_count", "fields"]` → extract `form_name` + any field with non-empty `event_handlers` for module derivation
- `03_database_rules.json`: iterate `payload.rules.rows[]` — each row follows schema `["type", "operation", "tables", "source_ref", "id"]` → extract `id` (DBR-NNN) + `tables[0]` + `operation` for repository test entries

**Rationale**: The `factored_array` headroom format with `schema[]` + `rows[]` is consistent across all three files and is already used by `solution-delphi.md` for business rule extraction. Parsing by index against the schema array is idiomatic for this artifact type.

**Alternatives considered**:
- Parse by key-name (not applicable — factored_array format uses positional rows)
- Use `extraction/` path which has pretty-printed format — decided to use `compressed/` first (token-optimized) with `extraction/` as fallback only

## Decision 2 — Path Resolution Order

**Question**: What is the authoritative path for the three AST JSON files?

**Decision**: Two-level resolution:
1. **Primary**: `projects/{project_name}/outputs/asis/delphi-ast-raw/compressed/{01_business_rules,02_form_business_rules,03_database_rules}.json`
2. **Fallback**: `projects/{project_name}/outputs/asis/delphi-ast-raw/extraction/{01_business_rules,02_form_business_rules,03_database_rules}.json`
3. **Hard stop**: if any of the three files is missing from both paths → BLOCKED, no output generated

**Rationale**: `compressed/` contains token-optimized (minified) variants generated by `run_delphi_ast_analysis.py` — preferable for LLM context window efficiency. `extraction/` contains the same data in pretty-printed/raw-fidelity format. Both are valid sources; `compressed/` is preferred for token efficiency. The spec attachment examples (`01_business_rules.json`, `02_form_business_rules.json`, `03_database_rules.json`) are from the `compressed/` path.

**Note on project_name**: The fallback path in the original spec draft referenced `projects/Meu-ERP_w_AST/` which was a specific project example. The implementation must use `{project_name}` dynamically — the `extraction/` fallback path is `projects/{project_name}/outputs/asis/delphi-ast-raw/extraction/`.

## Decision 3 — Essential FastQA Pipeline Steps

**Question**: Which FastQA steps are structurally required for test case generation?

**Analysis**:

| Step | Command | Essential? | Reason |
|---|---|---|---|
| load_pbi | `@fastqa:load_pbi` | ✅ Yes | Populates `pbi.current` — all subsequent agents depend on it |
| identify_gaps | `@fastqa:identify_gaps` | ✅ Yes | Mandated by spec requirement |
| estimate_effort | `@fastqa:estimate_effort` | ❌ No | Produces planning data not needed for test case content; `analyze_requirements` accepts it as optional |
| analyze_requirements | `@fastqa:analyze_requirements` | ✅ Yes | Produces `REQ-F-*` IDs that `map_behaviors` hard-blocks on |
| map_behaviors | `@fastqa:map_behaviors` | ✅ Yes | Produces `BHV-*` IDs used by `test_case_with_fastqa` for structured generation |
| ac_scope_analysis | `@fastqa:ac_scope_analysis` | ❌ No | Criticality classification is enhancement; `test_case_with_fastqa` has built-in fallback (all ACs treated as important) |
| test_case_with_fastqa | `@fastqa:test_case_with_fastqa` | ✅ Yes | Primary output — generates test case files |
| validate_scenarios | `@fastqa:validate_scenarios` | ❌ No | Quality improvement over existing test cases — does not block test case existence |
| test_plan (local) | manual generation from template | ✅ Yes | Required output for downstream phases |

**Decision**: Remove `estimate_effort`, `ac_scope_analysis`, `validate_scenarios`.

## Decision 4 — Test Plan Template Sections

**Question**: Which of the 9 template sections can be directly derived from the three AST JSON files?

| § | Section | Derivable from AST? | Verdict |
|---|---|---|---|
| 1 | Test Strategy — Pyramid | Fixed (no AST needed) | ✅ Keep |
| 2 | Unit Test Scope | `01_business_rules.json` (BRs → domain tests) + `02_form_business_rules.json` (event handlers → validator tests) | ✅ Keep |
| 3 | Integration Test Scope | `03_database_rules.json` (DB write ops → repository tests) | ✅ Keep |
| 4 | Architecture Tests | Not derivable — assumes Clean Architecture already decided (TO-BE concern) | ❌ Remove |
| 5 | E2E Tests | Requires `screen-navigation-map.md` and `value-chain.md` — removed from inputs | ❌ Remove |
| 6 | Smoke Test Suite | Generic boilerplate independent of any project data | ❌ Remove |
| 7 | Load Test Plan | Requires NFRs (throughput, concurrency) — absent from AST files | ❌ Remove |
| 8 | Test Data Management | Seed Data table requires `db/schema-inventory.md` — not in scope | ❌ Remove |
| 9 | Test Quality Gates | Fixed CI thresholds (no AST needed) | ✅ Keep |

**Decision**: Keep §§1, 2, 3, 9 (renumbered to §§1, 2, 3, 5). Add new §4 Test Coverage Map (traceability from AST rule IDs to test categories). Final template: 5 sections.

## Decision 5 — Orchestrator size_threshold

**Question**: Should the `size_threshold` for `qa/test-plan.md` be updated?

**Decision**: Reduce from 5000 bytes to 3000 bytes. The lean 5-section template produces a smaller but valid document. 3000 bytes is sufficient to detect genuine placeholder generation while not rejecting legitimate lean output. The threshold still serves its purpose: preventing generic `< 3KB` stubs from being accepted as complete test plans.

## Decision 6 — PBI Dispatch Trigger in Orchestrator

**Question**: Should the dispatch trigger `on(RF✓ + doc:RN✓)` be changed since we no longer need those artifacts?

**Decision**: Out of scope for this feature. The trigger is conservative (fires only after documentation is complete) and does not harm correctness — the bridge agent will simply ignore the documentation artifacts that now exist at that point. Changing the trigger would require a separate orchestrator spec.
