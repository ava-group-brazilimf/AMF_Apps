# Research — Architecture Blueprint Diagram Generation

## Decision 1 — Preserve phase-specific ownership

- **AS-IS Blueprint**: generated by `ava-asis-solution-delphi` for Delphi projects, with sibling solution agents owning their respective legacy technologies. Canonical Mermaid artifact: `projects/{project_name}/outputs/asis/diagrams/architecture-blueprint.mmd`.
- **TO-BE Blueprint**: generated by `ava-tobe-architecture-design`, dispatched by `ava-tobe-orchestrator` through trigger `CB`. Canonical Mermaid artifact: `projects/{project_name}/outputs/tobe/diagrams/architecture-blueprint.mmd`; companion document: `projects/{project_name}/outputs/tobe/docs/architecture-blueprint.md`.

**Rationale**: The repository already has two distinct architecture lifecycles. Introducing a single new producer would create ownership ambiguity and could overwrite AS-IS or TO-BE evidence.

## Decision 2 — Treat the Mermaid file as the render source of truth

The Summary builder must discover and sanitize the canonical `.mmd` artifact, inject it into `D.staticDiagrams` (`asisArchBlueprint` or `tobeArchBlueprint`), and the HTML renderer must consume that field through `renderAllDiagrams()` followed by `renderStaticDiagrams()`.

**Rationale**: The existing template already separates source injection from browser rendering. The failure is therefore diagnosed through the artifact lifecycle rather than by embedding a static diagram in the template.

## Decision 3 — Add explicit lifecycle status metadata and a blocking gate

A Blueprint quality record will distinguish:

- `MISSING_INPUT`
- `AGENT_NOT_EXECUTED`
- `GENERATION_FAILED`
- `MISSING_ARTIFACT`
- `DISCOVERY_FAILED`
- `RENDERING_FAILED`
- `PASS`

The record will include expected artifact, discovered artifact, generating agent, generation status, rendering status, project, and trace ID. Missing or unrenderable required artifacts block publication.

**Rationale**: The current UI fallback text collapses missing source and renderer failures into one presentation state, making remediation ambiguous.

## Decision 4 — Do not use placeholders as recovery artifacts

The TO-BE orchestrator currently documents a placeholder fallback for a missing `architecture-blueprint.mmd`. This must be replaced by an explicit failed gate/retry result. A placeholder must never be considered a valid Blueprint artifact or be published as architecture evidence.

**Rationale**: A placeholder satisfies file existence but violates artifact integrity and hides generation failure.

## Decision 5 — Reconcile document and diagram contracts without changing existing paths

The Markdown blueprint and Mermaid blueprint remain separate artifacts. The Mermaid file is mandatory for diagram publication; the Markdown file remains the architectural evidence document. Agent output contracts, module registries, Summary artifact maps, and validation checks must reference the same canonical paths.

**Rationale**: Existing consumers use both forms. Changing paths would be a breaking contract change and is unnecessary.

## Alternatives considered

1. **Generate the diagram in the Summary builder** — rejected because Summary is a consumer, not an architecture producer, and would violate phase ownership.
2. **Always synthesize a generic diagram** — rejected because it would hide missing upstream execution and invent architecture.
3. **Use the HTML blueprint as the only source** — rejected because HTML is a presentation artifact and cannot provide reliable source validation.
4. **Keep the current localized placeholder** — rejected because it cannot distinguish missing artifact, generation failure, and renderer failure.
